# Shared Claude Code Rules — Design Document

Date: 2026-02-13

## Problem

Claude Code rules (`.claude/rules/`) encode engineering standards that apply
across multiple projects. Today, each project maintains its own copy. When one
project discovers a better rule, the others don't benefit. Updating requires
manual copy-paste across repos.

## Goals

1. Single source of truth for engineering standards
2. Changes propagate instantly to all linked projects
3. Rules compose by technology stack (not all-or-nothing)
4. Project-specific values (design tokens, component catalogs) stay local
5. Personal use only — optimized for one developer's workflow

## Architecture

### Three layers

| Layer | Lives in | Delivery | Example |
| --- | --- | --- | --- |
| **Shared rules** | `claude-project-context` repo | Symlinked into project `.claude/rules/` | `typescript-web-types.md` |
| **Project config** | Each project's `CLAUDE.md` | Committed to project repo | Commands, structure, deployment |
| **Project rules** | Each project's `.claude/rules/` (non-symlinked) | Committed to project repo | `design-system.md`, MDX component catalog |

### Naming convention

Files are prefixed with their layer name: `<layer>-<topic>.md`.

This prevents naming collisions when symlinked into a flat `.claude/rules/`
directory and makes rule origin immediately visible.

### Composable rule sets

Each project selects rule sets via the install script. Typical combinations:

| Project type | Rule sets |
| --- | --- |
| Next.js site | `universal` + `typescript-web` + `nextjs` |
| Astro site | `universal` + `typescript-web` + `astro` |
| Flutter app | `universal` + `flutter` |
| Java Spring API | `universal` + `java-spring` |

## Install script

### Usage

```bash
# First time: interactive selection
python install.py /path/to/target-project

# Re-run: reads .manifest.json, re-applies same sets
python install.py /path/to/target-project --update

# Change selection
python install.py /path/to/target-project
```

### Behavior

1. Presents available rule sets with checkboxes
2. Creates `.claude/rules/` in target project if it doesn't exist
3. For each selected set, symlinks every `.md` file into the target
4. Skips files that already exist as non-symlinks (local overrides), prints warning
5. Replaces existing symlinks (safe re-run)
6. Writes `.manifest.json` recording selections and source path
7. Prints summary of linked, skipped, and updated files

### Manifest format

```json
{
  "source": "/Users/koi/Repositories/myersadamk/claude-project-context",
  "sets": ["universal", "typescript-web", "nextjs"],
  "installed": "2026-02-13"
}
```

## Rule content — merge strategy

### universal-review.md

**Sources:** Both projects' `review.md`

Framework-agnostic quality gate:

- Verification gate: `npm run lint && npm run typecheck && npm run format:check && npm run test && npm run build`
  - Projects MUST standardize on these script names in `package.json`
  - Skip `build` only for documentation-only changes
- Correctness checks: logic, edge cases, dead code, no `console.log`
- References other rules files for domain-specific checks
- Checklist structure (types, a11y, tailwind, security) with cross-references

### universal-security.md

**Sources:** Astro `security.md` + embedded rules from Next.js `best-practices.md`

- No secrets in source, `.env` not tracked
- Dependency policy: no additions without justification, audit new deps
- Input sanitization at system boundaries
- CSP awareness (framework-specific headers stay in framework rules)
- References `vibesec` skill for full security audits

### typescript-web-types.md

**Sources:** Astro `typescript.md` (richer, has examples) + Next.js `best-practices.md` TS section

- Strict mode non-negotiable
- `unknown` over `any` with code examples
- Type narrowing over `as` casting with code examples
- Naming: interfaces for shapes, types for unions, `ComponentNameProps` pattern
- Anti-pattern table (any, as, !, @ts-ignore, barrel files, enums)
- Explicit return types on functions

### typescript-web-tailwind.md

**Sources:** Both `tailwind.md` files

- Utility-first, no inline styles, no `!important`
- Class ordering: layout → sizing → spacing → typography → visual → interactive
- No arbitrary values without documented reason
- Colors from CSS custom properties only
- Mobile-first responsive (`sm:`, `md:`, `lg:`)
- Spacing: "MUST follow the project's design system scale" (values in local `design-system.md`)
- References `interface-design` skill for generating design tokens
- Anti-patterns: no `@apply` in components, no Tailwind in `<style>` blocks
- Component extraction over CSS classes for repeated patterns

### typescript-web-ui.md

**Sources:** Both `ui.md` files

- Semantic HTML: landmarks, heading hierarchy, correct element usage
- Accessibility: alt text, keyboard nav, focus states, ARIA labels, WCAG AA
- Responsiveness: mobile-first, 44px touch targets, no horizontal scroll
- Motion: design-system tokens, `prefers-reduced-motion`, transform-only hover
- Banned effects: glassmorphism, infinite gradients, parallax, auto-play

### typescript-web-best-practices.md

**Sources:** Next.js `best-practices.md` (non-TS sections)

- DRY: extract after 2 occurrences, co-locate first
- Naming: PascalCase components, camelCase utils, kebab-case data, boolean prefixes
- Imports: path alias (`@/`), no `../../`, grouped with blank lines
- Error handling: validate at boundaries only, no defensive code for impossible states
- File size: investigate at 200 lines
- Dependencies: no additions without discussion

### nextjs-architecture.md

**Sources:** Next.js `architecture.md` + shadcn parts of `ui.md`

- Server Components by default, `"use client"` only when needed
- State escalation ladder (data imports → useState → URL params → Context → stop)
- Data layer: `src/data/` typed arrays, no API routes unless requested
- Component organization: `ui/` (shadcn, don't modify), `components/`, `mdx/`
- shadcn/ui: use primitives first, compose don't modify, `HoverCardShell` for hover
- `cn()` for conditional classes
- No grab-bag directories

### nextjs-mdx.md

**Sources:** Next.js `mdx.md`

- Co-located `page.tsx` + `content.mdx` pattern
- `page.tsx` structure template (metadata, layout component, Content import)
- Heading rules (auto-generated anchors via `slugify()`)
- Component registration in `mdx-components.tsx`
- "MUST maintain an Available MDX Components table in a local project rules file"

### astro-framework.md

**Sources:** Astro `astro.md` + Astro-specific parts of `security.md`

- `.astro` components by default, framework components only for interactivity
- `<Image>` / `<Picture>` from `astro:assets`, never raw `<img>`
- Content collections with Zod schemas, query with `getCollection()`
- Client directives: `client:load` above-fold, `client:visible` below-fold
- Zero-JS default philosophy
- File-based routing, kebab-case, `getStaticPaths()` for dynamic routes
- No `innerHTML` / `set:html` with user content
- Client scripts MUST NOT fetch/eval external code

### astro-testing.md

**Sources:** Astro `testing.md`

- Unit: `tests/unit/` with Vitest, mirrors source structure
- E2E: `tests/e2e/` with Playwright
- What to test vs. don't test guidance
- Conventions: behavior over implementation, descriptive names

## What stays local per project

### CLAUDE.md (project root)

Each project maintains its own:

- Project overview and purpose
- Verification commands (using standard script names)
- Directory structure map
- Deployment instructions
- Content strategy / domain-specific notes

### .claude/rules/design-system.md

Project-specific design token values:

- Color tokens
- Spacing scale
- Typography scale
- Shadow levels
- Motion durations
- Component-specific constraints (border radius, etc.)

Generated by the `interface-design` skill or written by hand.
Shared rules reference this file but never define the values.

### Other local rules

- MDX component catalog (for Next.js/MDX projects)
- Content-specific rules (voice, tone, article structure)
- Any project-specific overrides of shared rules

## Verification command standardization

All typescript-web projects MUST define these scripts in `package.json`:

| Script | Purpose | Example implementation |
| --- | --- | --- |
| `lint` | Linter | `eslint .` |
| `typecheck` | Type checker | `tsc --noEmit` or `astro check` |
| `format:check` | Formatter check | `prettier --check .` |
| `test` | Test suite | `vitest run` (empty script if no tests yet) |
| `build` | Production build | `next build` or `astro build` |

The universal verification gate:

```bash
npm run lint && npm run typecheck && npm run format:check && npm run test && npm run build
```
